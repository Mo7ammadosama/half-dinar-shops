# Storing product photos in the cloud (closing blocker B1)

**The problem this fixes:** product photos are currently written to the server's own disk
(`backend/uploads/`). That disk is **temporary**. The next time the app is redeployed or the server
is replaced, **every photo the merchant ever uploaded is silently destroyed** — the products stay,
their pictures turn into broken images, and nothing anywhere reports an error.

For a shop with thousands of items, that is potentially weeks of the merchant's work gone.

The app is **fully built and wired for cloud storage**. No code needs to change. You are creating a
bucket and pasting four values into a config file. Unlike SMS, **there is no approval wait here** —
this takes about 15 minutes.

---

## It cannot ship broken by accident

The app **refuses to start in production** while photos would go to local disk. You will see:

```
Product photos would be stored on local disk, which is destroyed on redeploy.
Configure object storage: S3_BUCKET, S3_ACCESS_KEY_ID, ...
```

Local disk still works exactly as before in development, so nothing about your current testing
changes.

---

## Which provider I chose, and why

**Cloudflare R2.** Reasoning, so you can overrule it:

- **No egress fees.** This is the whole argument. Product photos are read constantly by every
  customer browsing the shop and downloaded far more often than they are uploaded. On AWS S3 you pay
  for every one of those reads; on R2 you do not. For an image-heavy catalogue this is the difference
  between a rounding error and a real monthly bill.
- **Generous free tier** — 10 GB of storage free. The pilot will not come close to that.
- It speaks the **standard S3 API**, so this is not a lock-in decision.

**The code is provider-neutral.** It is written against the S3 API, not against Cloudflare. R2, AWS
S3, Backblaze B2, DigitalOcean Spaces and MinIO all work by changing the endpoint and keys — no code
change. If you would rather use AWS S3, just leave `S3_ENDPOINT` unset and set `S3_REGION`.

## What you need to do (~15 minutes)

### Step 1 — Create a Cloudflare account and an R2 bucket

1. Sign up at <https://dash.cloudflare.com/sign-up> (free).
2. In the dashboard sidebar choose **R2**.
3. R2 asks for a payment card even to use the free tier. You will not be charged within the free
   allowance.
4. Click **Create bucket**. Name it `halfdinar-photos`. Leave the defaults.

### Step 2 — Make the bucket publicly readable

Customers' phones load these images directly, so the files must be readable without a key.

> **This is safe and correct.** Only product photos go in this bucket. Filenames are random UUIDs
> generated by the server, so nothing can be guessed or enumerated, and **no** customer data, order
> data, or personal information is ever stored here. Do not put anything else in this bucket.

1. Open the bucket → **Settings** → **Public access**.
2. Enable **R2.dev subdomain** (the quick option) — you get a URL like
   `https://pub-abc123.r2.dev`.
3. **Copy that URL.** It is your `S3_PUBLIC_BASE_URL`.

> Later, for a nicer URL and better caching, you can connect a custom domain
> (e.g. `photos.yourdomain.com`) instead. Set `S3_PUBLIC_BASE_URL` to that domain if you do.

### Step 3 — Create an API token

1. In **R2** → **Manage R2 API Tokens** → **Create API token**.
2. Permission: **Object Read & Write**.
3. Scope it to the `halfdinar-photos` bucket only (not "all buckets") — least privilege.
4. Click create. It shows you an **Access Key ID** and a **Secret Access Key**.

> ⚠️ **The secret is shown once.** Copy it now. If you lose it, delete the token and make a new one.

### Step 4 — Find your endpoint

On the R2 overview page, copy the **S3 API endpoint**. It looks like:

```
https://<your-account-id>.r2.cloudflarestorage.com
```

### Step 5 — Paste it all in

Add these five lines to `backend/.env`:

```bash
S3_BUCKET=halfdinar-photos
S3_ACCESS_KEY_ID=your_access_key_id
S3_SECRET_ACCESS_KEY=your_secret_access_key
S3_ENDPOINT=https://<your-account-id>.r2.cloudflarestorage.com
S3_PUBLIC_BASE_URL=https://pub-abc123.r2.dev
```

Restart the backend. **That is the whole change.** No code edits.

On startup you will see:

```
[StorageModule] Product photo storage: s3 (bucket halfdinar-photos at https://...)
```

If you instead see the "local disk — photos are LOST on redeploy" warning, one of the four required
values is missing or misspelled.

### Step 6 — Confirm it works

1. Open the merchant dashboard, edit a product, upload a photo.
2. The photo should display in the dashboard **and** in the customer app.
3. In the Cloudflare R2 dashboard, open the bucket — the file should be listed under `products/`.

## Cost

Free tier: **10 GB storage, 1 million writes/month, 10 million reads/month**, and **zero egress
fees**. A pilot shop with a few thousand photos will sit inside the free tier. Beyond it, storage is
about **$0.015/GB/month**.

---

## Important: photos already uploaded

Photos uploaded **before** you switch are on the old local disk and are **not** migrated
automatically. In practice this does not matter — the current photos are development test data, and
most seeded products have no photo at all (they show an emoji placeholder).

If real photos exist by then, re-upload them through the dashboard after switching. There are few
enough to be a manual job, and writing a migration script for test data would be wasted work.

## Reference — every storage setting

| Variable | Required? | Purpose |
|---|---|---|
| `S3_BUCKET` | for cloud | Bucket name |
| `S3_ACCESS_KEY_ID` | for cloud | API token key id |
| `S3_SECRET_ACCESS_KEY` | for cloud | API token secret |
| `S3_PUBLIC_BASE_URL` | for cloud | Public URL the photos are readable at |
| `S3_ENDPOINT` | R2/B2/Spaces/MinIO | S3-compatible endpoint. **Leave unset for real AWS S3.** |
| `S3_REGION` | no | Defaults to `auto` (R2's convention). Set a real region for AWS S3. |
| `S3_KEY_PREFIX` | no | Folder inside the bucket, default `products/` |
| `STORAGE_PROVIDER` | no | Force `local` or `s3`. Auto-detected when unset. |
| `UPLOAD_DIR` | dev only | Local folder when using disk storage |

## A bug this work found and fixed

Both the customer app and the dashboard built photo URLs by **always** prepending the API address to
whatever `image_url` held. That is correct for a local path (`/uploads/x.jpg`) but wrong for a cloud
URL, producing:

```
http://localhost:3000https://pub-abc123.r2.dev/products/x.jpg
```

**Every product photo would have silently stopped loading the day you switched to cloud storage** —
no error, no crash, no failing test. Just broken images, and a very confusing afternoon.

Both clients now pass absolute URLs through untouched, and there is a test
(`mobile/__tests__/imageSrc.test.ts`) pinning both shapes so it cannot regress.

## What I verified, and what I could not

**Verified (real, automated tests — `backend/test/storage.e2e-spec.ts`, 15 tests):**

- Local storage genuinely writes the file: the test **reads the bytes back off disk** and compares
  them to what went in, rather than trusting that a promise resolved.
- Two uploads never collide on a filename.
- Providing credentials switches storage to S3 with **no code change**; removing them falls back to
  local. Half-configured credentials are refused rather than silently using disk.
- The exact S3 request is correct: bucket, content type, body bytes, and a **server-generated key**
  that the client cannot influence (`products/<uuid>.jpg`).
- An upload failure surfaces to the merchant instead of returning a URL pointing at nothing — they
  must not believe a photo saved when it did not.
- **Production refuses to boot on local disk.**
- **The Phase 2 security rules survived the refactor** — re-tested, not assumed: a script disguised
  as `innocent.png` is still rejected on its magic bytes, and a customer still cannot upload at all.

**NOT verified — needs your account:**

- **A real upload to a real R2 bucket.** This needs a Cloudflare account with a payment card, which I
  cannot create. Everything up to the S3 API boundary is tested against the real AWS SDK
  (`@aws-sdk/client-s3`), including the exact command sent. What only you can confirm is that the
  bucket accepts it and the public URL serves it — that is Step 6 above.
